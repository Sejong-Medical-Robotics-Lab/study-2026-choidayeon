# 학습일지 — 2026-08-12 (Week 4, Go2 사족보행 + Gazebo)

## 오늘 배운 것
- Gazebo에 "Classic"과 "새 세대(Ignition → Gazebo Fortress/Garden/Harmonic)" 두 계보가 있고, 서로 명령어(`gazebo` vs `gz sim`)·플러그인 이름(`libgazebo_ros_*.so` vs `gz-sim-*-system`)·설정 방식이 전혀 다르다는 것
- 같은 apt 저장소라도 CPU 아키텍처(arm64 vs amd64)에 따라 실제로 받을 수 있는 패키지가 다를 수 있다는 것 — 지금 실습 환경(Ubuntu 22.04 arm64)에는 Gazebo Classic 바이너리 자체가 Ubuntu 공식 저장소에도 OSRF 공식 저장소에도 없었음
- `apt-cache policy` / `apt-cache madison`으로 특정 패키지가 "후보 없음(설치 불가)"인지 그냥 못 찾은 건지 구분해서 원인을 진단할 수 있다는 것
- 저장소 자체의 의존성이 깨져 있을 수도 있다는 것 — `libignition-gazebo6`(6.18.0)이 요구하는 `libignition-sensors6 >= 6.8.1`이 arm64 저장소엔 6.8.0까지밖에 안 올라와 있었음(소스 패키지는 6.9.0까지 있는데 arm64용 바이너리 빌드만 저장소에 안 올라온 상태) — 이런 경우는 내 로컬 설정 문제가 아니라 빌드팜이 따라올 때까지 기다리거나 소스 빌드로 우회해야 하는 문제라는 것
- URDF는 `gz sdf -p` 같은 변환 도구로 SDF로 바꿀 수 있고, ROS 브릿지가 전혀 없어도 `<mesh>` 경로만 절대경로로 맞춰주면 신버전 Gazebo에 로봇 모델을 물리 시뮬레이션과 함께 올릴 수 있다는 것
- snap으로 설치된 프로그램은 confinement 때문에 `$HOME` 하위 파일만 읽을 수 있고 `/tmp` 등 바깥 경로는 기본적으로 접근이 막힌다는 것(변환 작업을 홈 디렉터리 안에서 해야 했던 이유)

## 직접 해본 것 / 성공한 것
- snap으로 Gazebo(Harmonic, 8.9.0) 설치 후 기본 씬 실행까지 확인
- 기존 `go2-edu` 저장소가 Gazebo Classic(`gazebo_ros`) 전용으로 짜여 있다는 걸 README·launch 파일·URDF의 `<plugin filename="libgazebo_ros_...">` 블록에서 직접 확인
- arm64 환경에서 Classic Gazebo도, 대체재인 Ignition Fortress도 apt로 설치가 안 되는 걸 각각 원인까지 진단(Classic: 바이너리 자체 부재 / Fortress: 저장소 의존성 결함)
- ROS 브릿지 없이 우회하는 경로로 전환: `go2_sim.urdf`에서 Classic 전용 플러그인(`planar_move`, `joint_state_publisher`, `joint_pose_trajectory`, imu/lidar 퍼블리셔) 제거 + mesh 경로(`package://` → 절대경로)를 고쳐서 `go2_clean.urdf` 생성
- `gz sdf -p go2_clean.urdf`로 SDF 변환 → 기존 `mission.world`(벽 4개·장애물 3개·waypoint 3개)에 go2 모델을 이식해서 `go2_mission.world` 완성
- `gz sim -r go2_mission.world` 실행 후 `gz service`로 go2 엔티티 pose 조회 + 스크린샷으로 로봇이 실제 물리 시뮬레이션 위에서 렌더링되는 것 확인(다만 다리를 잡아주는 컨트롤러가 없어서 중력으로 주저앉은 자세로 안착)
- 기립 자세로 세우려고 기존 `kinematics.py`의 `stand_pose()` 함수를 그대로 돌려서 목표 관절각(hip=0, thigh=0.79, calf=-1.58, 12축 모두 동일)을 정확히 계산해봄 — 이 값을 gz-sim의 `JointPositionController` 시스템 플러그인(ROS 불필요)으로 넣어 기립시키는 작업까지 진행하다가 오늘은 중단

## 막힌 것 / 이해가 안 되는 것 (다음 Q&A 때 질문할 목록)
- ROS 2 arm64 저장소의 `libignition-sensors6` 바이너리 지연이 실제로 언제쯤 해소되는지, 이런 저장소 결함을 학생 입장에서 확인할 수 있는 공식적인 방법(빌드팜 대시보드 등)이 있는지
- 지금 방식(URDF→SDF 변환 + Classic 플러그인 제거)은 `go2_sim`의 sport mode 관제 노드(`/cmd_vel`, SportClient API, `/go2/lowstate` 등)와 완전히 끊어진 "모델만 있는" 상태인데, 나중에 이 관제 노드를 gz-sim 쪽과 다시 잇는 정석적인 방법이 ROS 브릿지 복구 말고도 있는지
- `JointPositionController`의 p/i/d 게인을 오늘은 감으로 넣었는데(p=60, i=0.5, d=2), 다리처럼 하중을 버텨야 하는 관절의 게인을 원칙적으로 어떻게 잡아야 하는지

## 한 줄 소감
파고들수록 Gazebo Classic/신버전 계보 차이, 아키텍처별 패키지 가용성, 저장소 자체의 의존성 결함까지 이어지면서 "설치가 안 된다"는 한 문장 뒤에 얼마나 많은 원인이 겹쳐있을 수 있는지 알게 됐다. 막혔다고 거기서 멈추는 대신 ROS 브릿지를 우회해서 해봤는데 더 봐야할 거 같음
